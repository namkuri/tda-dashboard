# 연구 정련소 — 문서→프로젝트 이관 도출 파이프라인 개선 계획

> 작성 r249 시점. 목적: 사용자가 정의한 **인과적 도출 의도**(키워드 Tree → 공정태그별 Task → 의존도 정렬 → 기간기반 Sprint → STAGE 마일스톤 → WBS+타임라인, 일관된 *concept Stream*)와 **현재 구현(r246–249)**을 비교하고, LLM이 그 의도대로 도출하도록 치밀하게 설계한다. **이 문서는 구현 전 검토용 계획**이며 아직 코드 변경은 없다.

---

## 0. 핵심 통찰 — "독립 추천" vs "인과 Stream"

| | 현재 (r247–249) | 사용자 의도 |
|---|---|---|
| LLM 호출 | **1회**로 5개 배열을 한꺼번에 | **단계별 도출**, 앞 단계 결과가 뒤 단계 입력 |
| 산출물 관계 | stages/wbs/sprints/issues/wiki가 **서로 무관**하게 병렬 | 키워드→Task→Sprint→STAGE→WBS가 **하나의 체인**으로 연결 |
| 공정/직무 태그 | 미사용 | Task 도출의 **핵심 기준**(PM_TAX 62개) |
| 의존도 | 없음 | Task 간 의존 → **위상정렬**로 순서 결정 |
| Sprint 분할 | LLM이 임의 추천 | **순서 + 기간(공수)** 기반 분할 |
| STAGE | LLM이 독립 추측 | **도출된 Sprint/Task를 집계**해 마일스톤 정의 |
| WBS | LLM이 독립 그룹핑 | STAGE/Sprint/Task를 **분류에 따라 배치 + 타임라인 순서** |
| 프로젝트 맥락 | LLM이 모름(빈 캔버스 가정) | **기존 STAGE/WBS/Sprint/태그를 이해**하고 적합 위치 판단 |
| Wiki | 작업 항목과 같은 화면에 섞임 | **작업과 분리** — 분류체계 기반 Well-Defined 게임요소 |
| UI | 평면 체크박스(인과관계 소실) | **Stream 시각화**로 선별 판단 용이 |

> 결론: 현재 구현은 "5종 항목 일괄 추천기"이고, 사용자가 원하는 것은 **bottom-up 도출 엔진**이다. intake 를 단일 호출에서 **다단계 파이프라인**으로 재설계해야 한다.

## 1. 현재 상태 정밀 진단 (재사용 가능 자산 포함)

### 1-A. 연구 정련소 현행 (r246–249)
- **③ 분해**: `refinery/structure.py analyze_structure()` — md 헤더 목차 + 키워드 **빈도/2-그램**(로직), 또는 `decomposer.py`(LLM). 노드 형식 `{id,title,kind(category|concept),summary,parent_id,ai_confidence,source_refs[]}`.
- **④ 들여오기 추천**: `refinery/intake.py propose_intake()` — `_structure_outline(nodes)` 트리 텍스트 1개를 LLM에 주고 **단일 호출**로 `{stages,wbs(+tasks),sprints,issues,wiki}` JSON 반환. 각 배열 독립.
- **생성**: `apply_ops.apply_work()` — stages→`product_stages`, sprints→`sprints`, wbs/tasks/issues 삽입. **상호 참조·공정태그·세그먼트·의존성 없음**.
- **⑤⑥ 위키**: `wiki_compose.compose_wiki_body()` — 채택 목차→본문→`apply_tree`.
- 한계: ①②③④ 모두 인과 단절. STAGE.tags(공정) 비움. sprint는 빈 주차. wbs는 segment/타임라인 미설정.

### 1-B. 마인드맵 고도화 추출기 (재사용 1순위)
- `POST /mindmap/generate` → `mindmap_generator.py generate_mindmap()` — **단일/다중/auto** 모드. 출력: `diagram{nodes,edges}` + `branches_raw{central, branches[{title,origin,children}], cross_links[{from,to,label}]}`.
- 강점: **메타 누출 필터 202종**(시스템 메시지 격리), **다중 문서 공통개념+cross_links**(문서 간 관계), **첨부(PDF/DOCX/HTML) 본문 통합**(`_mmpExpandHtmlEmbeds`).
- `POST /mindmap/explain` → NotebookLM식 노드 설명 + 후속질문(인용 각주).
- **정련소 분해보다 우수**: 관계(cross_links)·다중문서 클러스터링·누출방지. **단, ai_confidence/kind 없음 → 변환 필요**.

### 1-C. 프로덕트 관리 — STAGE + PM_TAX 공정/직무 태그 (도출 기준)
- `product_stages`: `id,project_id,name,type,goal(md),lifecycle,tags(jsonb[]),tag_meta(jsonb{}),status,sort_order`.
  - `type` ∈ **MVP|PoC|Prototype|Pilot** (검증 목적)
  - `lifecycle` ∈ **planning|build|gtm|iterative** (개발 단계)
  - `tags[]` = PM_TAX 소분류 id 배열, `tag_meta{tagId:{assignee,goal,deliverables[]}}`
- **PM_TAX** (`index.html` ~32031–32094): **62개 소분류**, 3계층(대>중>소), 5대분류(게임기획/아트/프로그래밍/사운드/운영QA). 각 `{i,p,v,s(축약),l(전체)}`. 예: `3.1.2 게임 로직`, `2.2.4 애니메이션`, `5.1.1 빌드 검수`. + `product_taxonomy` 커스텀.
- STAGE = "팀이 향해갈 방향 이미지". 운영 페이지에서 **소분류 태그별 담당자/목표/산출물(문서·태스크)**.
- 현 연결: STAGE↔Sprint/WBS **직접 링크 없음**. Task는 deliverable 경유로 `desc`에 "Stage:…·태그경로" 기재, 문서는 `meta.stageId/stageTag`.

### 1-D. WBS / 타임라인 / Sprint / Task 모델 (도출 종착지)
- `wbs_nodes`: `id,parentId,title,desc,status,progress,links{},assignees,segments`.
- **`links._segments[]`**(핵심): `{id,start,due,sprintIds[],taskIds[],issueIds[],deps[{n,s}],color,_legacy}` — **막대별 독립 일정 + 세그먼트→세그먼트 의존성**. 그 외 `links`: `sprintIds,taskIds,issueIds,categoryIds,_estimated_days,node_ids,depends_on,linkIds(레거시 WBS-WBS 의존)`.
- `tasks`: `id,catId,title,desc,priority,status,zone(now|shelf|buried),sprintId,dueDate,assignees,linkedDocIds,issueIds`. **공정태그 필드 없음**(현재 desc 텍스트로만).
- `sprints`: `weekLabel,goal,status(planning|active|closed),startDate,endDate,milestoneCriteria[],carryoverFromPrevious[],intrusion*`.
- 관계: `task.sprintId→sprint`, `wbs.links.taskIds/sprintIds→`(역참조), 의존성=레거시(노드) + segment.deps(세그먼트). **위상정렬/기간기반 분할 로직은 아직 없음**.

## 2. 의도 vs 현재 — 11개 항목 갭 분석

| # | 사용자 의도 | 현재 | 갭 / 해야 할 일 |
|---|---|---|---|
| 1 | 키워드 추출 + Tree화 | structure.py 빈도 또는 decompose LLM | **마인드맵 추출기 재사용** 경로 추가(cross_links 포함) → 정련소 노드로 변환 |
| 2 | Tree 노드별 **공정태그 기준 Task 도출** | 공정태그 미사용, WBS→task 일반 분할 | PM_TAX를 LLM에 주입, 노드별로 **공정태그 부착 Task** 도출 |
| 3 | Task **의존도 → 진행순서** | 없음 | LLM이 의존 edge 추론 + **로직 위상정렬** |
| 4 | 순서+기간 → **Sprint 분할** | LLM 임의 빈 주차 | **공수 기반 그리디 패킹**(의존성 준수) + LLM 명명 |
| 5 | Sprint/Task → **STAGE(마일스톤) 정의** | STAGE 독립 추측 | Sprint 묶음을 **집계**해 STAGE(type/lifecycle/tags) 도출 |
| 6 | STAGE/Sprint/Task → **WBS 분류 + 타임라인 순서** | wbs 독립 그룹핑, segment 없음 | 분류 기준 WBS 배치 + **`_segments`(start/due/deps)** 자동 구성 |
| 7 | **Bottom-up** 운영 반영 | top-down 일괄 | 파이프라인 자체가 bottom-up. 채택 시 실제 테이블 반영 |
| 8 | Wiki = 작업 무관, **분류체계 Well-Defined** | 위키가 work와 섞임 | Wiki **별도 분기** + **게임요소 분류체계**(작업/순서 배제) |
| 9 | 일반문서 = **연구문서 보관** | 미구분 | 문서 유형 분기: 보관-only 경로 |
| 10 | LLM이 **기존 프로젝트 이해**하고 배치 판단 | 빈 캔버스 가정 | 모든 호출에 **프로젝트 컨텍스트** 주입 |
| 11 | **일관된 Stream**, 선별 판단 쉬운 UI | 평면 체크박스 | **Stream 데이터 모델 + 시각화 UI** |

## 3. 제안 아키텍처 — 다단계 도출 파이프라인 (LLM 설계 중심)

> 원칙: **로직이 할 수 있는 건 로직**(위상정렬·기간패킹·집계), **판단이 필요한 것만 LLM**(공정 분류·의존 추론·명명·배치). 각 단계는 SSE로 진행 노출. 모든 산출물은 `stream` 역참조를 달아 체인 유지.

### 파이프라인 개요
```
③ 분해(Tree)         → nodes[] (+cross_links)        [마인드맵 추출기 재사용]
   ↓
④-1 Task 도출        → tasks[]  (node_id, process_tag, hours)   [LLM: 공정 분류]
④-2 의존도          → tasks[].depends_on + order            [LLM edge + 로직 topo]
④-3 Sprint 분할      → sprints[] (task_ids)                  [로직 패킹 + LLM 명명]
④-4 STAGE 정의       → stages[] (sprint_ids, type, tags)     [LLM 집계]
④-5 WBS+타임라인     → wbs_nodes[] (_segments, deps)         [로직 배치 + LLM 분류]
   ↓ 채택
apply: product_stages / sprints / tasks / wbs_nodes (+ stream 메타)
별도 분기: Wiki(분류체계 Well-Defined)  /  일반문서(보관)
```

### ④-1. Task 도출 — 공정태그 기준 (LLM)
- **입력**: Tree 노드(잎=concept) + cross_links + **PM_TAX 목록**(id·축약·전체) + **프로젝트 컨텍스트**(§5).
- **LLM 역할**: 각 노드에 대해 "이 개념을 게임으로 구현/완성하려면 어떤 **공정**의 어떤 작업이 필요한가?" → 1~2일(4~16h) 단위 Task 도출, 각 Task에 **PM_TAX 소분류 id** 부착.
- **프롬프트 핵심 규칙**(시스템 메시지):
  1. 반드시 제공된 PM_TAX **id 중 하나**를 `process_tag`로 선택(목록 외 금지).
  2. Task는 **결과물 중심**(예: "콤보 판정 로직 구현"), 4~16h.
  3. 한 노드가 여러 공정에 걸치면 공정별로 분할.
  4. 기존 프로젝트에 **이미 있는 작업과 중복되면 생략**(컨텍스트 참조).
  5. JSON only.
- **출력 스키마**:
  ```json
  { "tasks": [
    {"id":"t1","title":"콤보 판정 로직 구현","desc":"...","node_id":"k1",
     "process_tag":"3.1.2","est_hours":8,"deliverable_kind":"code|art|design|doc"}
  ] }
  ```
- **Stream 연결**: `task.node_id`(키워드 출처) + `task.process_tag`(공정). → `tasks` 테이블에 **신규 필드 `process_tag`** 필요(또는 `links`/jsonb stash, §7 결정).

### ④-2. 의존도 정렬 (LLM edge + 로직 topo)
- **입력**: ④-1 tasks + cross_links(개념 관계 힌트).
- **LLM 역할**: Task 쌍 의존 추론 — "A가 B의 선행"인 edge만. (예: "캐릭터 컨트롤러" → "콤보 입력 처리").
- **로직 역할**: edge로 **위상정렬**(Kahn) → 선형 order + 병렬 가능 그룹(레벨). 순환 감지 시 경고 + 약한 edge 절단.
- **출력**: `task.depends_on[]` + `task.order`(정수) + `task.parallel_group`.
- **재사용**: 의존성은 최종적으로 WBS `segment.deps[{n,s}]`로 매핑(§④-5).

### ④-3. Sprint 분할 (로직 패킹 + LLM 명명)
- **입력**: order된 tasks + est_hours + **사용자 설정 용량**(스프린트 길이 주, 팀 가용 시간/주 — UI 입력).
- **로직 역할**: order를 따라 **누적 공수 ≤ 용량**으로 그리디 패킹, 단 **선행 Task와 같은/이전 스프린트 금지**(의존 위배 방지). 스프린트 경계 = 용량 초과 시 분리.
- **LLM 역할**: 각 스프린트 묶음에 **week_label·goal**(그 묶음이 달성하는 한 줄 목표) 생성.
- **출력**:
  ```json
  { "sprints":[{"id":"s1","week_label":"2026 W23","goal":"콤보 코어 동작",
                "task_ids":["t1","t3"],"seq":1}] }
  ```
- **Stream 연결**: `sprint.task_ids` ↔ 각 `task.sprint_id`.

### ④-4. STAGE 정의 — 마일스톤 집계 (LLM)
- **입력**: ④-3 sprints + 그 안의 tasks의 **공정태그 분포** + 프로젝트 컨텍스트(기존 STAGE).
- **LLM 역할**: 연속 스프린트들을 **하나의 제품 목표(마일스톤)**로 묶어 STAGE 정의.
  - `name`(방향성 이미지), `type`(MVP/PoC/Prototype/Pilot), `lifecycle`(planning/build/gtm/iterative), `goal`(md).
  - `tags[]` = 그 STAGE 스프린트들의 **실제 공정태그 합집합**(추측이 아니라 도출된 작업에서 역산 → 방향성이 근거를 가짐).
  - `tag_meta` seed = 공정별 목표/예상 산출물(담당자는 비움, 사용자가 운영 페이지서 지정).
- **출력**:
  ```json
  { "stages":[{"id":"st1","name":"전투 코어 MVP","type":"MVP","lifecycle":"build",
     "goal":"...","sprint_ids":["s1","s2"],"tags":["3.1.2","1.1.1"],
     "tag_meta":{"3.1.2":{"goal":"...","deliverables":["콤보 로직"]}}}] }
  ```
- **Stream 연결**: `stage.sprint_ids` ↔ 각 `sprint.stage_id`. (sprints/product_stages 신규 참조 필드, §7.)

### ④-5. WBS 분류 + 타임라인 (로직 배치 + LLM 분류)
- **입력**: stages/sprints/tasks + **기존 WBS 트리**(컨텍스트).
- **LLM 역할**: 도출 작업을 WBS로 **분류** — 신규 WBS 노드 생성 vs **기존 WBS에 부착** 판단(분류 기준: 공정 대분류 또는 STAGE). 각 WBS의 parent 결정.
- **로직 역할**: 각 WBS 노드의 **`links._segments`** 자동 구성 —
  - 세그먼트 = 그 WBS가 담는 스프린트(들). `start/due` = 스프린트 `startDate/endDate`(없으면 seq×기간 추정).
  - `sprintIds/taskIds` 채움. `deps[{n,s}]` = task `depends_on`을 **세그먼트 의존**으로 변환.
  - `_estimated_days` = 공수 합/8.
- **출력**: `wbs_nodes[{id,parentId,title,desc,links{taskIds,sprintIds,_segments[...],_estimated_days,node_ids,_source_session}}]`.
- **Stream 연결**: `wbs.links.node_ids/taskIds/sprintIds` + `_segments.deps` → 타임라인이 곧 도출 순서.

## 4. (요약) 단계별 LLM/로직 분담표

| 단계 | LLM | 로직 | 신규 백엔드 |
|---|---|---|---|
| ③ 분해 | 키워드/구조(마인드맵 재사용) | 헤더 목차(기존) | `decompose`에 mindmap 경로 |
| ④-1 Task | 공정분류·작업도출 | — | `refinery/derive_tasks.py` |
| ④-2 의존 | edge 추론 | 위상정렬 | `refinery/order.py`(로직) |
| ④-3 Sprint | 명명 | 공수 패킹 | `refinery/sprintize.py` |
| ④-4 STAGE | 집계·정의 | tags 역산 | `refinery/stagize.py` |
| ④-5 WBS | 분류·배치 | 세그먼트/deps | `refinery/wbsize.py` |

> 호출 횟수↑ 대신 **각 단계 캐싱 + 부분 재실행**(앞 단계 결과 고정하고 한 단계만 재도출)로 비용·재현성 관리.

## 5. 프로젝트 컨텍스트 인식 (의도 #10)

모든 ④ 단계 LLM 호출에 **압축 프로젝트 상태**를 주입한다(신규 헬퍼 `refinery/context.py build_project_context(project_id)`):
```
[기존 STAGE]  - 전투 코어 MVP (MVP/build) tags: 3.1.2,1.1.1
[기존 WBS]    - 전투 시스템 / └ 입력 처리 / 무기 밸런싱
[기존 Sprint] - 2026 W21(closed) 2026 W22(active)
[공정 태그]    PM_TAX 62개 (id·축약)
[칸반 카테고리] 기획, 클라, 아트 ...
```
- 효과: ④-1은 **중복 작업 생략**, ④-4는 **기존 STAGE 확장 vs 신규** 판단, ④-5는 **기존 WBS에 부착**.
- 출처: 프론트가 `currentData`(wbsNodes/sprints/categories) + product_stages를 요청에 동봉(백엔드는 Supabase 직조회도 가능).

## 6. Concept Stream 데이터 모델 (의도 #11)

세션 1회 도출 = `stream_id`. 모든 산출물에 **역참조**를 달아 체인 추적:
```
node(keyword)  ─┐
                ├─ task   { node_id, process_tag, depends_on[], order, sprint_id, stream_id }
                │            ↓
                ├─ sprint { task_ids[], stage_id, seq, stream_id }
                │            ↓
                ├─ stage  { sprint_ids[], tags[], stream_id }
                │            ↓
                └─ wbs    { links.node_ids/taskIds/sprintIds, _segments.deps, _stream_id }
```
- **신규 필드 최소화 전략**(미마이그레이션 DB 보호, r249 교훈): 전용 컬럼 대신 **기존 jsonb에 stash** —
  - task: `tasks`에 컬럼 추가 부담 → **`links` 없음** → 대안: `details`/신규 `meta` jsonb, 또는 process_tag만 신규 컬럼(검토 §7).
  - sprint/stage/wbs: `links`·`tag_meta`·`generated_tree` 등 기존 jsonb 활용.
- UI가 `stream_id`로 한 도출 묶음을 한 화면에 모아 **계보 렌더**.

## 7. 미해결 결정사항 (사용자 확인 필요)

1. **분해 추출기**: ③에 마인드맵 추출기(`/mindmap/generate`)를 **재사용**할지(권장), 정련소 자체 분해를 마인드맵 품질로 끌어올릴지.
2. **공정태그 저장**: `tasks.process_tag` **신규 컬럼**(마이그레이션 필요) vs `details`/jsonb stash(무마이그레이션). STAGE↔Sprint, Sprint↔Task **참조 필드**도 동일 결정.
3. **스프린트 용량 입력**: 주당 가용 시간/스프린트 길이를 사용자 입력으로 받을지, 기본값(예 2주·40h) 고정할지.
4. **STAGE 집계 단위**: 1 STAGE = N 스프린트 자동 묶음 기준(공정 전환점? 제품 목표?)을 LLM 자율 vs 규칙.
5. **Wiki 분류체계**: 게임요소 Well-Defined용 표준 분류(시스템/세계관/캐릭터/레벨/밸런스…)를 고정 템플릿으로 제공할지.
6. **UI 형태**: Stream을 칸반식 5열(노드→Task→Sprint→STAGE→WBS) 흐름으로 볼지, 트리 드릴다운으로 볼지.

## 8. 단계별 구현 로드맵 (검토 승인 후 진행)

> 각 Phase는 **문법 검증(AST+node --check) + Preview 부팅** 후 커밋. LLM·DB 실동작은 GPU 서버+Supabase에서 사용자 검증.

- **Phase A — 컨텍스트 & 분해 재사용**: `context.py build_project_context`; ③ 분해에 마인드맵 추출기 경로(+cross_links→정련소 노드 변환). 의존: 결정 #1.
- **Phase B — Task 도출(④-1)**: `derive_tasks.py` + PM_TAX 주입 프롬프트 + 라우트 `/refinery/derive-tasks`(SSE). 프론트 ④ 화면 1열(노드별 Task + 공정 배지). 의존: #2.
- **Phase C — 의존+Sprint(④-2·3)**: `order.py`(위상정렬) + `sprintize.py`(패킹) + 명명 LLM. 용량 입력 UI. 의존: #3.
- **Phase D — STAGE(④-4)**: `stagize.py` 집계 + tags 역산. 기존 STAGE 확장 판단. 의존: #4.
- **Phase E — WBS+타임라인(④-5)**: `wbsize.py` segment/deps 구성. `apply_work` 확장(stream 메타·segment 기록).
- **Phase F — Stream UI**: 5단계 계보 시각화 + 단계별 채택/부분 재도출. apply 시 실제 테이블 + stream_id stash.
- **Phase G — Wiki/일반문서 분기**: 문서 유형 판정(작업화 vs 위키화 vs 보관). 위키는 게임요소 분류체계 템플릿. (현 ⑤⑥ 재활용.)

## 9. 리스크 & 검증 전략

- **로컬 LLM JSON 신뢰도**: 단계 분할로 각 호출 출력이 작아져 파싱 안정↑. 모든 파서 `_extract_json`(코드펜스·trailing comma 복구) 재사용 + 단계별 [] 기본값.
- **호출 비용/지연**: 단계 캐싱 + "한 단계만 재도출". 노드/Task 상한 + 초과 시 `log` 노출(무음 절단 금지).
- **미마이그레이션 DB**: 신규 컬럼은 PostgREST 거부 위험(r249 교훈) → 우선 jsonb stash, 필요한 컬럼만 `db-schema-manual-migration` 절차로 안내.
- **기존 흐름 보존**: 현 r247–249 ④⑤⑥는 유지하며 파이프라인을 **점진 대체**(Phase별 토글), 구 함수/공용헬퍼 삭제 금지(refinery-flow-redesign 메모 참조).
- **검증 한계**: 클로드 환경은 문법/순수로직만. 위상정렬·패킹은 단위 테스트 가능(LLM 불요) → Phase C는 **로직 테스트로 강검증**.

## 10. 한 줄 요약
현재 "5종 일괄 추천기"를, **키워드→(공정)Task→(의존)순서→(공수)Sprint→(집계)STAGE→(분류)WBS+타임라인**으로 이어지는 **추적 가능한 bottom-up 도출 엔진**으로 재설계한다. LLM은 *공정 분류·의존 추론·집계·분류*만 맡고, *위상정렬·기간패킹·세그먼트 구성*은 로직이 맡으며, 모든 호출에 **기존 프로젝트 맥락**을 주입해 적합 위치를 판단한다. Wiki·일반문서는 작업 도출과 분리한다.
