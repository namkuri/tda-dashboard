# 위키 운영 전략 보고서 — 문서 중심에서 개념(관계) 중심으로

> 팀 논의(ethaniya · 우희성 · namkyu)에서 도출된 위키/기획문서 관리 문제와 해결 아이디어를 정리하고,
> **인디팀(한정된 인력) 기준 최적 운영안**을 도출한다.

---

## 0. 한 줄 요약 (TL;DR)

기획이 자주 바뀌는데 문서가 서로 강하게 얽혀 있어, **하나가 바뀌면 줄줄이 고치고 다시 검수해야 하는 "연쇄 수정/검수" 비용**이 핵심 문제다.
해법은 **위키를 "문서 단위"가 아니라 "개념(관계) 단위"로 재편**하는 것 — BM·시스템·디자인 같은 **단일·비중복 정의 문서**를 만들고, 서사형 문서는 이를 **참조만** 하게 한다.
그러면 변경이 "어느 개념이 바뀌었나"로 환원되어 **해당 정의 1개만 수정 → 참조 문서에 '재검수 필요' 신호 전파**로 끝난다(선형 검토 → 병렬 검토).
태그/승인/자동화는 **"관리가 또 다른 일이 되지 않는" 선에서 경량**으로 운영한다.

---

## 1. 배경과 절대 제약

- **누구**: 인디팀, 인력 한정. → 운영 부담이 곧 생존 비용.
- **무엇**: 게임 기획 → 위키(프로젝트 위키/정전). 기획이 **자주, 크게** 바뀜.
- **이미 가진 것**: 연구 정련소(기획문서 분해→분류→위키), 프로젝트 위키 **승인 딱지**(파란 배지+히스토리, 1인 강제통과 가능), 수동 문서 버전, `[[위키링크]]` 상호 참조, 분류체계(taxonomy) 페이지(0=분류체계 설명, 1=기획에서 추출한 기능 분류).
- **절대 원칙(우희성, 반복 강조)**: **유지보수가 최우선.** "일하는 게 편한 것"보다 **"이 위키를 관리하는 일이 추가 업무가 되지 않는 것"**이 더 중요. 관리 안 되면 *정보가 아니라 데이터 홍수*가 난다. → **과한 분류·과한 상세 서술은 지양.**

## 2. 겪고 있는 / 우려하는 문제

### 2-1. 연쇄 의존성(Cascade) — **핵심 문제**
> 최하위 문서 A(검수됨)에서 B·C가 파생. C를 만들다 A를 고쳐야 하면 → A 수정 → A에 의존한 B 수정 → 다시 A·B·C 전부 재검수. 연결이 커질수록 폭발. (우희성)

문서들이 서로 **강하게 결합(tight coupling)**되어, 한 곳의 변경이 **하류로 줄줄이 전파**된다. 검토자는 매 변경마다 **여러 문서를 선형으로** 비교해야 한다.

### 2-2. 하위 개념 결합 취약성 — "S6 문제" (**팀이 이름을 못 붙인 그것**)
> 문서 안에서 설명용으로 정의한 약칭/개념(예: "S6")에 다른 문서들이 의존. S6가 삭제·변경되면 그 개념을 쓴 **모든 문서를 찾아 고쳐야** 한다. (우희성)

이건 소프트웨어로 치면 **누수되는 추상화(leaky abstraction) / 단일 실패점(SPOF) 개념 의존**이다. "a~z로 설명할게요" 했던 기획이 다음에 "ㄱ~ㅎ으로 설명할게요"로 바뀌면, 과거 문서를 전부 매핑·수정해야 하는 거대한 매니징이 생긴다.

### 2-3. 철 지난 문서(Outdated) 누적
> 과거 대화/기획이 다 저장돼 있는데, 바뀌기 전 기획까지 AI가 다 읽으면 컨텍스트가 "터진다." (우희성/ethaniya)

오래된·폐기된 내용이 쌓이면 최신성과 충돌하고, AI가 옛 버전을 근거로 잘못 작동한다.

### 2-4. 최신성·검수 불확실성 (기간/검수 태그의 필요)
> "이 문서가 지금 최신 기획과 차이가 있는지 없는지" 기계도 사람도 모른다. (ethaniya)

- **기간별**: 언제 작성/갱신됐는지(자동) → "오래됐으니 확인 필요" 신호.
- **검수별**: 사람이 최신 기획과 대조해 확인한 시점(수동). 더 나아가 **"확정/고정(추가 검수 불필요)"** 여부가 가장 우선.
- **승인(결재)과의 차이**: 승인=작성 후 정식 승격(사전). 검수=이후 문서들이 더 쌓여도 계속 해야 하는 **무결성 점검(사후/상시)**. → 별개지만 비슷한 메커니즘 재활용 가능.

### 2-5. "잠금 태그가 수정을 막는 역설"
> 사람: "이게 새 버전이야" / AI: "검수된 태그 붙은 건 못 바꿔!" (우희성, 반농담)

검수/고정 태그를 **하드 잠금**으로 쓰면, 정작 고쳐야 할 때 사람이 태그를 일일이 빼야 하는 **새로운 수작업**이 생긴다.

### 2-6. 버전 감지 취약
> 지금은 수동 버전 변경뿐 → 변경이 확실히 안 잡힌다. (namkyu)

### 2-7. 승인 시스템의 과잉 관리 우려
정식 승격 게이트가 인디팀엔 과한 매니징이 될 수 있다. 쓸지 말지는 **운영 효율로 판단**.

## 4. 우리에게 맞는 최적 운영안 (종합 권고)

> 위 아이디어를 **유지보수 최우선·인력 최소** 기준으로 묶으면, 한 줄로: **개념 중심 2-레이어 + 경량 태그 + 의존성 전파.**

### 4-1. 핵심 전환 — 위키를 2개 레이어로

```
정의 레이어 (Canon / 정의서)        ← 단일·비중복·가능한 한 불변
  BM        ┐
  시스템     ├─ 각 개념당 정의 문서 1개 (인벤토리란? 광고 BM이란?)
  디자인     ┘    서로 포괄하지 않음. 약칭 대신 보편 언어로.

서술 레이어 (서사 / 참조서)          ← 정의를 [[참조]]만 해서 엮음
  게임 루프 / 온보딩 / 빌드 …         자체 정의 금지(상위→하위 참조 규칙)
```

- **효과**: 모든 기획 변경이 **"어느 개념이 바뀌었나"**로 환원됨 → **해당 정의 문서 1개만 수정**.
  B에서 BM이 안 바뀌었으면 BM 문서는 그대로, C에서 BM 변경이 필요하면 **BM 문서 하나만** 고침. (우희성 C/D)
- **검토 비용**: 문서별로 A↔B↔C 다중 비교(선형) → **개념별 단일 대조(병렬)**. 검토자는 "마지막에 떠든 내용"만 해당 정의와 맞춰보면 됨. (우희성 H)
- **S6 문제 차단**: 정의 문서는 **짧고 핵심만**, 내부 약칭 의존 금지. 약칭이 필요하면 정의 문서 안에서만 닫히게. (A)

### 4-2. 불변/확정은 "개념(레이어)에" 표시 — 문서마다 X
- "인벤토리=확정 시스템"처럼 **정의 레이어 노드에 `확정` 플래그**. 그러면 그걸 참조하는 A·B·C 문서가 누구든 **변경 무의미** → 문서별로 "고치지 마" 할 필요 없음. (F)
- **상향식**: 게임 컴포넌트의 **덜 바뀌는 바닥부터** 확정해 올라간다.

### 4-3. 참조 규칙 (의존을 한 방향으로 강제)
1. **상위 개념(서술서)만 하위 개념(정의서)을 참조**해 설명할 수 있다.
2. **형제 참조 시, 형제가 설명하는 부분만** 참조한다(전체 포괄 금지).
→ 의존 그래프를 **단방향·얕게** 유지 → 캐스케이드 차단. (G)

### 4-4. 경량 태그 4종 (자동/수동 명확히)

| 태그 | 의미 | 부착 | 용도 |
|------|------|------|------|
| `작성/갱신일` | 언제 만들어졌나 | **자동** | 오래되면 "확인 필요" 신호(기간별) |
| `검수: 누가·언제` | 사람이 최신 기획과 대조 확인 | **수동** | 최신성 보증 |
| `확정/불변` | 추가 검수 불필요, 변경 지양 | **수동**(개념/레이어 단위) | 변경 동결 표시 |
| `재검수 필요` | 참조 정의가 바뀜 → 다시 보라 | **자동 전파** | 2-5 역설의 해법 |

- **핵심 — "잠금"이 아니라 "신호"로**: 검수/확정 태그를 **하드 잠금으로 쓰지 않는다.** 정의가 바뀌면 그걸 참조하는 문서에 **`재검수 필요`를 자동으로 달아** "다시 봐라"라고 알릴 뿐, 수정을 막지 않는다. (ethaniya/namkyu: "센싱해서 사용자 옵션으로")

### 4-5. 의존성 추적 + 재검수 전파 (선형→병렬의 엔진)
- 각 문서 **상단(frontmatter)에 참조(의존) 명시** → AI가 읽어 **의존 그래프** 구성. (B)
- 정의 문서가 바뀌면 → **하류 참조 문서에 `재검수 필요` 자동 부착**.
- 검토자는 **"재검수 필요" 큐**만 보면 됨 → 전체 순회 불필요.

### 4-6. AI staleness sweep (사람 손 덜 타게)
- 주기적으로 AI가 **정의↔서술 불일치, 죽은 약칭(S6류), 철 지난 표현**을 감지해 **취소선/플래그**.
- **자동 삭제는 지양** — 위험하니 "표시 + 사람 1클릭 확인". (I, 단 우희성 "유지보수가 핵심" 원칙 반영)

### 4-7. 승인은 경량·선택
- 정식 승격이 꼭 필요한 **소수 문서**에만 승인 사용. 대부분은 **검수 태그로 충분.**
- 강제 통과 허용 유지(과한 게이트 X). (2-7)

### 4-8. 운영 원칙 (요약)
- **간결·핵심.** 정의 문서는 짧게, 내부 약칭 의존 금지, 약칭은 보편어로 풀어쓰기.
- **안 만들어도 되는 문서는 안 만든다.** 분류·태그 최소.
- **역할 분담**: 추출·전파·sweep = **AI**, 확정/검수 판단 = **사람**. 사람 일은 *"마지막에 떠든 것만"* 검토.

## 5. TDA Dashboard 적용 매핑 (있는 기능으로, 단계적)

| 운영안 | 지금 있는 것 | 손볼 것 |
|--------|-------------|---------|
| 정의 레이어 생성 | **연구 정련소**(분해 logic-first + 개념 단편화, 기획문서와 무관한 개념풀 추출) | 분류체계(BM/시스템/디자인)를 **정의서 폴더 구조**로 고정 |
| 정의서/서술서 구분 | 프로젝트 위키 kind(canon/wiki) | "정의서=canon, 서술서=wiki" 규약 + 서술서는 **참조만** 린트 |
| 참조·의존 추적 | `[[위키링크]]`, `linked_doc_ids` | frontmatter `참조:` + 의존 그래프 + **변경 시 하류 `재검수 필요` 전파** |
| 태그 | 승인 딱지·버전·히스토리 | `작성일(자동)`·`검수(수동)`·`확정`·`재검수 필요(자동)` 태그 + 필터 |
| outdated 정리 | 위키 감사(wiki_auditor)·정련소 | **staleness sweep**(취소선/플래그) + 재검수 대시보드 |
| 승인 | 승인 요청→배지→히스토리 | 정식 소수에만 사용(경량) |

### 권장 롤아웃(작게 시작)
- **1단계(MVP)**: 분류체계 폴더 확정(BM/시스템/디자인) → 핵심 **정의서 몇 개**부터 단일·비중복으로 작성 + `확정` 표시 + `작성일` 노출. *(여기까지만 해도 절반은 해결)*
- **2단계**: frontmatter `참조` + 정의 변경 감지 → `재검수 필요` 자동 전파.
- **3단계**: AI staleness sweep + 재검수 큐 대시보드.

## 6. 트레이드오프·주의 (과설계 경계)

- **초기 재구성 비용**: 기존 문서를 개념별로 쪼개는 1회성 작업 필요. → 핵심 개념부터 점진 이행.
- **쪼개기의 역설**: 너무 잘게 나누면 *그 관리*도 비용. → "추정 단위를 **문서별로** 본다"는 팀 잠정 합의 유지(개념 폭발 방지). 정의서는 **굵직한 개념** 위주.
- **완벽주의 금지**: 우희성 말대로 *"안 해도 별 문제 없다, 하자면 이렇다"* — **필수가 아니라 점진 개선.** 유지보수 부담이 늘면 즉시 단순화.

## 7. 결론

문제의 본질은 **"강결합된 문서들의 연쇄 수정·검수"**이고, 가장 큰 위험은 **S6류 약칭 의존(누수 추상화)**이다.
해답은 **개념 중심 2-레이어(정의서/참조서) + 단방향 참조 규칙 + "잠금 대신 재검수-신호" + AI 자동 추적/sweep**으로,
**선형 검토를 병렬 검토로 바꿔** 인디팀의 관리 비용을 구조적으로 낮추는 것이다.

**다음 액션(제안)**: ① 불변/확정 카테고리(분류체계) 먼저 합의 → ② 정의서 3~5개 시범 작성 → ③ `재검수 필요` 자동 전파를 정련소/위키에 시범 적용. 부담되면 1단계에서 멈춰도 효과는 충분.
